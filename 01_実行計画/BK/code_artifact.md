# 脱・初学者からDBAへ！ 実行計画の読み方とクエリチューニング入門

## 1. はじめに（前提条件とゴール）

### 本資料の対象読者
- 基本的なSQL構文（`SELECT`, `FROM`, `WHERE`, `INNER JOIN` / `LEFT JOIN` など）の意味がわかる方
- 「SQLを書いてみたものの、処理が遅いときにどう調べればいいかわからない」と悩んでいる方
- 将来的にデータベース管理者（DBA）や、パフォーマンスチューニングに強いバックエンドエンジニアを目指す方

### 到達ゴール
1. 実行計画が「何のために」「どのように作られるか」の基本原理（オプティマイザと統計情報の関係）を理解する。
2. 実行計画のツリー構造を見て、**どのステップからどのような順序で実行されるか**をトレースできるようになる。
3. `Full Scan` と `Index Scan`、`Nested Loops` と `Hash Join` の違いを理解し、クエリ遅延時の初期切り分けができるようになる。

## 2. 実行計画とは何か？

### 2.1 手続き型言語とSQLの決定的な違い
Java、Python、Go などの手続き型言語では、「データをどうやってループさせて探すか」という**手順（How）**をエンジニア自身がコードに記述します。

一方、SQLは**非手続き型（宣言型）言語**です。
```sql
SELECT customer_name, order_date
FROM orders
WHERE total_amount >= 10000;
```
エンジニアが指示しているのは「10,000円以上の注文データが欲しい」という**目的（What）**だけであり、「どのファイルをどの順番で開いて探すか」という手順は一切指定していません。

### 2.2 実行計画の正体
この「どうやって探すか」という具体的な内部処理手順を、データベース内部の頭脳である**オプティマイザ（Optimizer）**が自動で組み立てます。その決定された作業指示書・ナビゲーションルートが**「実行計画（Execution Plan）」**です。

```
[クライアント]
     |  SQL文（What: 何が欲しいか）
     v
[RDBMS: パーサー]
     |  構文解析・権限チェック
     v
[RDBMS: オプティマイザ]  <--- ★ここで複数の探索ルートを比較検討
     |  実行計画（How: 具体的な手順書）を決定
     v
[RDBMS: エグゼキュータ]
     |  ストレージやバッファからデータを取得・結合
     v
[検索結果]
```

## 3. オプティマイザと「統計情報」の重要性（DBAの基礎）

現代の主要なRDBMS（Oracle, PostgreSQL, MySQL等）は、**コストベース・オプティマイザ（CBO: Cost-Based Optimizer）**を採用しています。

### 3.1 コスト（Cost）とは？
オプティマイザは、考えられる複数の実行経路（テーブルを直接探すか、インデックスを使うか、どちらを先に結合するか等）をシミュレーションし、それぞれの**推定負荷（ディスクI/O回数、CPU消費量など）**を計算します。この推定負荷の相対数値を**コスト**と呼びます。
オプティマイザは、**「最もコストが低い実行計画」**を1つ選んで実行します。

### 3.2 統計情報（Statistics）の役割
コストを計算するための判断材料が**「統計情報」**です。
- テーブルに現在何行格納されているか
- 使用しているデータブロック（ページ）の総数
- 各列にどのような値が分布しているか（カーディナリティ、NULLの割合）
- インデックスの階層数（B-Treeの深さ）

> 💡 **DBA視点のワンポイント**
> 
> オプティマイザは**「統計情報という名の地図」**を見てルートを決めています。
> テーブルに100万件のデータがあるにもかかわらず、統計情報が古くて「10件」と記録されていた場合、オプティマイザは「全件読んでも一瞬で終わる」と誤認して最悪のルート（非効率な全表走査など）を選択してしまいます。
> **「SQLが急に遅くなった」というトラブルの現場で、真っ先に統計情報の最終収集日時を確認するのはDBAの基本動作です。**

## 4. 実行計画の3大構成要素

実行計画を読み解く際は、まず以下の3つの観点に着目します。

### 4.1 アクセスパス（データの探し方）
テーブルやインデックスから行を抽出する方法です。

| アクセスパス名 | 概要 | 特徴・使いどころ |
| :--- | :--- | :--- |
| **TABLE ACCESS FULL**<br>(Full Table Scan / Seq Scan) | テーブル全体のブロックを先頭から末尾まで走査する。 | **数千件以下の極小テーブル**や、**テーブル全体の数割以上を取得する全件集計**では最速。数百万件から数件を引く場合は致命的な遅延原因になる。 |
| **INDEX UNIQUE SCAN** | 一意インデックス（主キーや一意制約）を走査する。 | 該当行が最大1行であることが保証されているため、B-Treeをルートからリーフまで1回辿るだけで終了する最速アクセス。 |
| **INDEX RANGE SCAN** | 非一意インデックスを範囲走査する。 | 範囲条件（`>` や `BETWEEN`）や、重複値を持つインデックス列の検索時に使用。インデックスで絞り込んだ後、実テーブルを見に行く（ROWID参照）。 |

### 4.2 結合アルゴリズム（複数テーブルの繋ぎ方）
複数のテーブルを `JOIN` する際の内部処理方式です。

#### 1. Nested Loops Join（入れ子ループ結合）
- **仕組み**: プログラミングの二重ループと同じです。外側（駆動表）の1行ごとに、内側（内部表）のインデックスを都度検索します。
- **適したケース**: 駆動表の行数が十分に絞り込まれており、内部表の結合キーにインデックスが存在する場合。

#### 2. Hash Join（ハッシュ結合）
- **仕組み**: 片方のテーブル（通常は小さい方）の結合キーをメモリ上に展開してハッシュテーブルを作成し、もう片方のテーブルを走査しながらハッシュ値を突き合わせて結合します。
- **適したケース**: 大量データ同士の結合、または結合キーにインデックスが存在しない場合。

#### 3. Sort Merge Join（ソートマージ結合）
- **仕組み**: 双方のテーブルを結合キーでソートし、先頭から突き合わせていく方式です。不等号結合（`>` など）や、あらかじめデータがソートされている場合に選ばれます。

### 4.3 見積もり値（Cost / Rows）
- **Cost**: 推定負荷。
- **Rows (Cardinality)**: その操作によって結果として何行出力されるかの**「推定件数」**。

## 5. 実行計画を読んでみよう（実例と読み順ルール）

### 5.1 読み順の黄金ルール
実行計画はツリー（階層）構造で表示されます。処理順序を追うルールは以下の3点のみです。

1. **インデント（字下げ）が最も深い行**から実行される。
2. インデントが同じ階層の場合、**上にある行**から順に実行される。
3. **親ステップは、子ステップの結果を受け取って**初めて処理を行う。

### 5.2 サンプルケース
以下のSQLの実行計画を読み解きます。

```sql
-- 会員(users)テーブルと注文(orders)テーブルを結合し、
-- 2026年10月以降の注文を抽出する
SELECT u.user_name, o.order_id, o.order_date
FROM users u
INNER JOIN orders o ON u.user_id = o.user_id
WHERE o.order_date >= '2026-10-01';
```

#### 表示された実行計画の例（ツリー形式）
```text
-------------------------------------------------------------------------------------------------
| Id  | Operation                     | Name              | Rows  | Cost | 実行順序
-------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT              |                   |   500 |   42 | ⑤ (最終結果)
|   1 |   NESTED LOOPS                |                   |   500 |   42 | ④
|   2 |     TABLE ACCESS BY INDEX ROWID| ORDERS            |   500 |   12 | ②
|*  3 |       INDEX RANGE SCAN        | IDX_ORDERS_DATE   |   500 |    3 | ① (ここから開始)
|   4 |     TABLE ACCESS BY INDEX ROWID| USERS             |     1 |    1 | ③
|*  5 |       INDEX UNIQUE SCAN       | PK_USERS          |     1 |    0 | 
-------------------------------------------------------------------------------------------------
※ * が付いている行は検索条件（Predicate Information）が適用されている箇所
```

#### ステップごとの解説
1. **【ステップ①：Id=3】**
   最もインデントが深い `INDEX RANGE SCAN (IDX_ORDERS_DATE)` が最初に動きます。注文日インデックスを使って、2026年10月以降の注文インデックスエントリ（約500件）を特定します。
2. **【ステップ②：Id=2】**
   特定したROWIDを使って `ORDERS` テーブルの実データを取得します。
3. **【ステップ③：Id=5 → Id=4】**
   注文データ1行ごとに、その `user_id` を使って `USERS` テーブルの主キーインデックス（`PK_USERS`）を1件検索し、会員名を取得します。
4. **【ステップ④：Id=1】**
   外側の `ORDERS` と内側の `USERS` を1行ずつ突き合わせます（`NESTED LOOPS`）。
5. **【ステップ⑤：Id=0】**
   すべての行を結合し終えた結果セットをクライアントへ返却します。

## 6. よくあるスロークエリの原因とアンチパターン

現場で「インデックスを作成したはずなのに遅い」というクエリの多くは、実行計画を見ると `TABLE ACCESS FULL` に倒れています。

### パターン1: 検索条件列を関数や計算式でラップしている
```sql
-- [NG] 列に関数を適用しているため、B-Treeインデックスが利用できずFull Scanになる
SELECT * FROM orders WHERE TRUNC(order_date) = '2026-10-01';
SELECT * FROM products WHERE price * 1.1 > 5000;

-- [OK] 列側を裸にし、リテラル（右辺）側を計算・変換する
SELECT * FROM orders WHERE order_date >= '2026-10-01' AND order_date < '2026-10-02';
SELECT * FROM products WHERE price > 5000 / 1.1;
```

### パターン2: 暗黙の型変換（Implicit Type Conversion）
```sql
-- [NG] user_code 列が VARCHAR2(文字列) なのに数値を渡している
-- RDBMSが内部で TO_NUMBER(user_code) = 12345 に変換するためインデックスが無効化される
SELECT * FROM users WHERE user_code = 12345;

-- [OK] 型を一致させて渡す
SELECT * FROM users WHERE user_code = '12345';
```

### パターン3: 前方一致以外のLIKE検索
```sql
-- [NG] 中間一致・後方一致は、B-Treeの左端からのソート順が使えないためFull Scanになる
SELECT * FROM users WHERE user_name LIKE '%田中%';
SELECT * FROM users WHERE user_name LIKE '%田';

-- [OK] 前方一致であればインデックスレンジスキャンが可能
SELECT * FROM users WHERE user_name LIKE '田中%';
```

## 7. DBAとしてのトラブル調査チェックリスト

遅いSQLの調査を依頼されたときは、以下のフローで切り分けを行います。

```markdown
- [ ] 1. 実行計画の取得
      - 単なる EXPLAIN（推定値）だけでなく、可能であれば実際の実行時間や処理行数がわかる
        実測情報（PostgreSQL: EXPLAIN ANALYZE / Oracle: DBMS_XPLAN.DISPLAY_CURSOR）を取得したか？

- [ ] 2. フルテーブルスキャンの確認
      - 大規模テーブルに対して TABLE ACCESS FULL が発生していないか？
      - 発生している場合、適切なインデックスが存在するか？ 構文によって無効化されていないか？

- [ ] 3. 見積もり件数（Rows）と実測件数の乖離チェック
      - 実行計画上の Rows は数件なのに、実際には数十万件処理されていないか？
      - 乖離が大きい場合、統計情報が古くなっていないか？（`ANALYZE` の再実行を検討）

- [ ] 4. 結合方式の妥当性
      - 数十万件同士の巨大テーブル結合で Nested Loops が選択され、大量ループしていないか？
      - メモリが不足して Hash Join がディスクI/O（Temp領域への退避）を起こしていないか？
```

## 8. 次のステップ（さらにスキルアップするために）
- **実測値（Actual）の分析**:
  オプティマイザの「予想」と「実際の実行結果」を比較するスキルを身につける。
- **インデックス設計**:
  単一列インデックスだけでなく、複数列の複合インデックスの列順序（選択度と等価条件の優先順位）を学ぶ。
- **統計情報収集の自動化運用**:
  夜間バッチやデータ急増時の統計情報メンテナンス設計を理解する。
