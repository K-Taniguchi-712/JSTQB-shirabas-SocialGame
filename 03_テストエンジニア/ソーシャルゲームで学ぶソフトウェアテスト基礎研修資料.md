## 第1章 テストの基礎

### 1.1 テストとは何か？ テスト目的とデバッグとの違い

ソフトウェアテストとは、単に「アプリを操作してバグを探すこと（テスト実行）」だけではありません。計画・分析・設計・レビュー・進捗管理など、品質を評価し運用時の故障リスクを減らすための一連の知的活動すべてを指します。

テストには**検証（Verification）**と**妥当性確認（Validation）**の2つの視点があります。また、実際にゲームを動かして確認する**動的テスト**と、動かさずに企画書やソースコードを確認する**静的テスト**の両輪で進めます。

> **ソシャゲでの具体例（新ガチャ実装）**
> * **検証：** 仕様書通りに「SSR排出率3%・300連で天井交換」が実装されているか確認する。
> * **妥当性確認：** 実際のプレイヤーにとって排出演出や交換導線がわかりやすく、納得感があるか確認する。
> * **テストとデバッグの違い：** QAがテストで「10連ガチャでエラー落ちする（故障）」を発見するのが**テスト**。エンジニアが再現させ、原因箇所を特定（診断）し、コードを修正するのが**デバッグ**です。修正後は、同じ人が直ったかを見る**確認テスト**と、他のガチャが壊れていないかを見る**リグレッションテスト**を行います。

### 1.2 なぜテストが必要か？ QA・QCと「エラー・欠陥・故障」の連鎖

テストは**品質コントロール（QC：プロダクト指向の是正活動）**の一種であり、完成品や中間成果物の欠陥を見つけて修正につなげます。一方、**品質保証（QA：プロセス指向の予防活動）**は「そもそもミスが起きにくい開発・テストの仕組み」を整えることです。

不具合は次の連鎖で発生します。
人間がミスをする（**エラー**） → 仕様書やコードに誤りが混入する（**欠陥／バグ**） → 実行時に想定外の動きになる（**故障**）。
再発を防ぐには、エラーを生んだ背景である**根本原因**を取り除くことが重要です。

> **ソシャゲでの具体例（SSR確率設定ミス）**
> 深夜作業で疲れたプランナーが入力ミスをする（**エラー**） → マスタデータに「0.03」ではなく「0.30」と記載される（**欠陥**） → リリース後にSSRが30%で排出され緊急メンテナンスになる（**故障**）。原因を調べると「リリース前日に1人で手入力していた」ことが判明（**根本原因**）。マスタの自動バリデーション導入が**QA**、リリース前の実機テストが**QC**です。

### 1.3 テストの7原則

長年のソフトウェア開発の経験から導き出された7つの普遍的な原則は、ソーシャルゲームの現場でもそのまま当てはまります。

| テストの原則 | ソーシャルゲーム開発・運用での意味 |
| :--- | :--- |
| **1. 欠陥があることは示せるが、ないことは示せない** | テスト環境で100回ガチャを回して異常が出なくても、「バグがゼロである」と証明することはできない。リスクを減らす活動と捉える。 |
| **2. 全数テストは不可能** | 全キャラ × 全装備 × 全スキル × 全ステージ × 全スマホ機種・OSの組み合わせをすべて試すのは不可能。技法とリスクで優先順位を絞る。 |
| **3. 早期テストで時間とコストを節約** | 企画書段階で「報酬の重複配布」に気づけば数分で直せるが、リリース後に発覚すると緊急メンテ・データロールバック・お詫び対応で莫大なコストがかかる。 |
| **4. 欠陥の偏在（パレートの法則）** | バグの大部分は一部の複雑な機能（新規バトルギミック、マルチプレイ同期処理、複雑な特効計算など）に集中する。重点的にテスト工数を割く。 |
| **5. テストの弱化** | 毎回同じイベント用チェックリストをなぞるだけでは、新仕様特有のバグをすり抜けてしまう。テストデータや観点を継続的に見直す必要がある。 |
| **6. テストはコンテキスト次第** | 課金決済やデータ引き継ぎは極めて厳密にテストする一方、1日限定のエイプリルフール企画はスピードと演出重視で軽量にテストするなど状況に合わせる。 |
| **7. 「欠陥ゼロ」の落とし穴** | 仕様書通りバグゼロで実装しても、ロードが長すぎて周回がつらい、報酬が魅力的でないイベントならプレイヤーは離脱する。妥当性確認が不可欠。 |

### 1.4 テストプロセス・テストウェア・トレーサビリティと役割

テスト活動は、**テスト計画 → モニタリングとコントロール → テスト分析（何をテストするか） → テスト設計（どうテストするか） → テスト実装（データ・環境準備） → テスト実行 → テスト完了**の7活動で構成されます。各活動で作られる成果物（計画書、テストケース、テストデータ、欠陥レポートなど）を**テストウェア**と呼びます。

企画書（テストベース）の要件と、テストケース・実行結果・発見したバグを紐づけておくこと（**トレーサビリティ**）により、「今回のコラボイベントの要件はすべて確認済みか」「仕様変更でどのテストを再実行すべきか」を瞬時に判断できます。

### 1.5 必要なスキル・チーム全体アプローチ・テストの独立性

テスト担当者には、テスト技法や技術知識に加え、プレイヤー目線のドメイン知識、細部へのこだわり、批判的思考が求められます。特にテスト担当者は「バグがある」という悪い知らせを伝える立場になりやすいため、個人を責めず事実を建設的に伝える**コミュニケーションスキル**が極めて重要です。

アジャイルなゲーム開発では、プランナー・エンジニア・QA全員が品質に責任を持つ**チーム全体アプローチ**が有効です。一方で、作成者自身の思い込み（確証バイアス）を外すため、**テストの独立性**（開発者自身 → 同チーム → 社内独立QA → 外部デバッグ会社）を適切に組み合わせます。独立性が高いほど別視点のバグを見つけやすい反面、開発と孤立したりボトルネック化したりするリスクに注意が必要です。

## 第2章 ソフトウェア開発ライフサイクル全体を通してのテスト

### 2.1 開発モデル（SDLC）・シフトレフト・DevOps・ふりかえり

テストの進め方は開発モデルに合わせて調整します。新規タイトルの立ち上げなど大規模な初期開発ではシーケンシャル型（V字モデル等）が使われることがあり、リリース後の隔週イベント運用ではイテレーティブ／アジャイル型が主流です。どのモデルでも「すべての開発活動に対応するテスト活動を持つ」「仕様書ドラフトの段階からQAが関与する」ことが鉄則です。

* **シフトレフトアプローチ：** コード実装を待たず、企画・設計の初期段階（工程表の左側）から仕様レビューや静的解析、早期の非機能テストを開始する考え方。後工程の手戻りを劇的に減らします。
* **テストファースト開発（TDD／ATDD／BDD）：** 実装前にテストを定義する手法。例えばBDDでは「Given（前提：HPが10%以下） / When（操作：必殺技を発動） / Then（結果：ダメージ2倍）」のように自然言語で仕様とテストを兼ねます。
* **DevOpsとCI/CD：** 開発（QA含む）と運用が連携し、コード変更のたびに自動ビルド・自動テスト・マスタ検証を回す仕組み。頻繁なイベント更新でもリグレッションリスクを最小化できます。
* **ふりかえり（レトロスペクティブ）：** 大型イベント終了後やスプリント末に全員で「うまくいったこと・改善点」を議論し、次回のテストプロセスや仕様書テンプレートの改善につなげます。

### 2.2 テストレベル（5段階）とテストタイプ（4分類）

テストの「粒度・段階」を表すのが**テストレベル**、確認する「品質特性・観点」を表すのが**テストタイプ**です。

| 5つのテストレベル | ソーシャルゲームでの対象と具体例 |
| :--- | :--- |
| **コンポーネントテスト**（ユニットテスト） | 最小部品単体のテスト。ダメージ計算式、ガチャ抽選ロジック、経験値テーブル計算の関数単体を開発者が自動テストで確認する。 |
| **コンポーネント統合テスト** | 部品同士の連携テスト。スキル発動処理とバフ・デバフ管理モジュールのデータ受け渡しや計算順序を確認する。 |
| **システムテスト** | ゲームアプリ全体を通したエンドツーエンドのテスト。ホーム画面→編成→バトル→リザルト→報酬受取までの一連の流れと非機能特性をQAが検証する。 |
| **システム統合テスト** | 外部システムとの連携テスト。App Store / Google Play の課金決済、外部SNSアカウント連携、プッシュ通知配信サーバーとの接続を確認する。 |
| **受け入れテスト** | リリース準備完了の妥当性確認。プロデューサー・運営による確認（UAT）、サーバー監視手順の確認（運用受け入れ）、景品表示法・資金決済法の適合確認、ユーザー参加のクローズドβテストなど。 |

**4つのテストタイプ**は、すべてのテストレベルで組み合わせて使います。

* **機能テスト（何をするか）：** アイテム購入、フレンド申請、ギルドチャットなどの機能が仕様通り動くか。
* **非機能テスト（どれほどうまく動くか）：** ISO/IEC 25010に基づき、周年イベント開始時の同時アクセス耐性（**性能効率性**）、メモリ改ざん・チート耐性（**セキュリティ**）、片手操作のしやすさ（**使用性**）、各iOS/Android端末での動作（**互換性**）、通信切断からの復帰（**信頼性**）などを評価。
* **ブラックボックステスト：** 内部コードを見ず、企画書や画面仕様（外観）からテストを設計する。
* **ホワイトボックステスト：** ソースコードの分岐やデータフロー（内部構造）を見て網羅性を確認する。

### 2.3 メンテナンス（保守）テスト

リリース後の本番稼働中に行うテストです。以下の3つのきっかけで発生し、変更箇所のテストに加えて既存機能への悪影響がないか**影響度分析**とリグレッションテストを行います。

* **改良・修正：** 定期イベント追加、バランス調整、緊急バグ修正（ホットフィックス）。
* **移行・環境更新：** iOS/AndroidのメジャーOSアップデート対応、ゲームエンジン（Unity等）のバージョンアップ、クラウドサーバー移行時のデータ変換テスト。
* **廃棄（サービス終了）：** オフライン版へのデータ移行、資金決済法に基づく未使用有償通貨の払戻し手続きやユーザーデータの長期アーカイブ・復元テスト。

## 第3章 静的テスト

### 3.1 静的テストの基本と価値

静的テストは、ゲームを実行せずに成果物（企画書、イベント仕様書、マスタデータCSV、シナリオテキスト、ソースコード、テストケースなど）を評価する活動です。人間の目で行う**レビュー**と、ツールで機械的に調べる**静的解析**があります。

動的テストでは見つけにくい「仕様書の矛盾・曖昧さ」「到達不能なデッドコード」「コーディング規約違反」「シナリオの誤字脱字・禁則文字」を、実装前の最もコストが安い段階で直接発見できる点が最大の価値です。

### 3.2 レビュープロセス・役割・4つのレビュー種別

レビューは**「計画 → 立ち上げ → 個々人のレビュー → 共有と分析 → 修正と報告」**の5ステップで進めます。参加者は、**マネージャー**（リソース提供）、**作成者**（仕様書やコードの作成・修正）、**モデレーター**（進行・安全な場の維持）、**書記**（指摘の記録）、**レビューア**（精査）、**レビューリーダー**（全体責任）の役割を担います。

| レビュー種別 | 特徴とソーシャルゲーム現場での使い分け |
| :--- | :--- |
| **非形式的レビュー** | 決まった手順や記録は不要。隣席のプランナー同士でのチャット相談やペアプログラミングでの軽い確認など、手軽にミスを拾う。 |
| **ウォークスルー** | **作成者が主導**して成果物を説明。新イベント企画書をプランナーがエンジニア・QAに読み合わせし、認識合わせと疑問点の洗い出しを行う。 |
| **テクニカルレビュー** | **モデレーターが主導**し、技術専門家が参加。マルチプレイの通信設計やDB負荷対策など、技術的な妥当性の合意と欠陥検出を行う。 |
| **インスペクション** | **最も形式的**でメトリクス収集も行う。作成者はリーダーや書記を兼ねられない。課金決済仕様書やガチャ確率マスタなど、失敗が許されない重要成果物に適用。 |

**レビュー成功のコツ：** 「作成者の人事評価に使わない」「一度に大量の仕様書を見ず小さく分割する」「事前読み込みの時間を確保する」「チェックリストを活用し、心理的安全性を保つ」ことが不可欠です。

## 第4章 テスト分析と設計

### 4.1 テスト技法の3分類

勘や思いつきだけでテスト項目を作ると、漏れや重複だらけになります。シラバスでは、少ないテストケースで高い網羅性を得るための技法を、**ブラックボックス（仕様ベース）**、**ホワイトボックス（構造ベース）**、**経験ベース**の3つに分類しています。

### 4.2 ブラックボックステスト技法（4技法の実践例）

#### ① 同値分割法（EP）
同じ処理が行われる入力値をグループ（パーティション）に分け、各グループから代表値を1つずつテストします。仕様で許可された「有効パーティション」だけでなく、エラーになるべき「無効パーティション」も必ず含めます。

> **例（未成年者の月額課金上限仕様）**
> 「16歳未満：上限5,000円」「16歳以上18歳未満：上限20,000円」「18歳以上：上限なし」の場合、有効パーティションは3つ（例：12歳、17歳、25歳）、無効パーティションはマイナス値や不正な生年月日（例：-1歳、未来の日付）を設定し、各代表値でテストします。

#### ② 境界値分析（BVA）
バグが最も起きやすいパーティションの「境目（最小値・最大値）」を狙う技法です。境界値と隣接する1点を見る**2値BVA**と、境界値の両隣を見るより厳密な**3値BVA**があります。

> **例（ガチャ天井カウント仕様）**
> 「1〜299回は通常抽選、300回で天井報酬獲得」の境界（299と300）をテストする場合、2値BVAでは「299, 300」、3値BVAではさらに「298, 299, 300, 301」を確認します。`if (count == 300)` と `if (count >= 300)` の実装ミスなどを確実に仕留められます。

#### ③ デシジョンテーブルテスト
複数の条件の組み合わせによって結果が変わる複雑なルールを表に整理し、組み合わせの漏れや仕様矛盾を発見します。

| 条件 / アクション（イベント特効ボーナス） | ルール1 | ルール2 | ルール3 | ルール4 |
| :--- | :---: | :---: | :---: | :---: |
| 条件1：イベント開催期間内である | T | T | T | F |
| 条件2：特効キャラを編成している | T | T | F | - |
| 条件3：月額パスに加入している | T | F | - | - |
| **アクション：獲得ポイント 2.0倍** | **X** | | | |
| **アクション：獲得ポイント 1.5倍** | | **X** | | |
| **アクション：獲得ポイント 1.0倍（通常）** | | | **X** | **X** |

*※ T＝真（条件を満たす）、F＝偽、-＝結果に無関係、X＝そのアクションが発生。*

#### ④ 状態遷移テスト
システムの状態とイベントによる移り変わり（状態遷移図・状態表）をテストします。**全状態カバレッジ**（すべての状態を通る）、**有効遷移カバレッジ**（正しい遷移をすべて通る）、さらに禁止操作も試す**全遷移カバレッジ**があります。

> **例（クエスト進行の状態遷移）**
> 「未挑戦 →（開始）→ 挑戦中 →（ボス撃破）→ クリア」「挑戦中 →（通信切断）→ 中断中 →（再開）→ 挑戦中」といった有効遷移に加え、「クリア済み画面でバックキー連打して報酬を二重取得できないか」などの**無効な遷移**も1テストケースにつき1つずつ検証します。

### 4.3 ホワイトボックステスト技法

ソースコードの内部構造を見て網羅率（カバレッジ）を測ります。コード内のすべての実行可能な行を通す**ステートメントカバレッジ**と、if文のTrue/Falseなどすべての分岐を通す**ブランチカバレッジ**があります。

**重要ポイント：** ブランチカバレッジ100%を達成すればステートメントカバレッジ100%も自動的に保証されますが、逆は成り立ちません。例えば「属性相性が有利ならダメージ1.5倍（if文のみ、elseなし）」のコードでは、有利属性だけテストすれば全行通過（ステートメント100%）になりますが、不利・等倍時の分岐（ブランチ）が未テストのまま残ってしまいます。

### 4.4 経験ベースのテスト技法

仕様書に書ききれない現場特有のバグを見つけるため、QA担当者の知識と経験を活かします。

* **エラー推測（フォールト攻撃）：** 「ソシャゲでありがちなバグ」を先読みして突きます。例：日付跨ぎ（0:00 / 4:00リセット）、端末時刻の手動変更、決済ボタン連打、ガチャ演出中のタスクキル、機内モード切替、絵文字・特殊文字のニックネーム入力など。
* **探索的テスト：** アプリを触って学習しながら、テスト設計・実行・評価を同時に進めます。時間枠（例：60分）と目的（**テストチャーター**：「新キャラのスキルが既存ボス全種に与える挙動を探る」）を決めて行う**セッションベースドテスト**が効果的です。
* **チェックリストベースドテスト：** 過去の不具合知見を質問形式のリスト（「アプリをバックグラウンドから復帰した際、BGMは正常に鳴るか？」等）にまとめ、定期的に更新しながら使います。

### 4.5 コラボレーションベースのテストアプローチ

バグを「見つける」だけでなく、チーム全員の対話で「未然に防ぐ」アプローチです。ユーザーストーリーを**3つのC（カード・会話・確認）**と**INVEST基準**（独立・交渉可能・価値・見積り可能・小さい・テスト可能）で共同執筆し、**受け入れ基準**をシナリオ指向（Given/When/Then）やルール指向で明確化します。実装前に受け入れ基準からテストケースを作る手法が**受け入れテスト駆動開発（ATDD）**です。

### 4.6 【新人QA向け演習】ブラックボックステスト技法 実践ワーク

現場に配属されて最初に担当することが多い「仕様書からのテストケース作成」を想定した3つの演習です。まずは自力でテストデータや表を書き出してから、下の解答・解説を確認しましょう。

#### 演習1：同値分割法 ＆ 境界値分析（アイテムショップのまとめ買い割引）
**仕様：** ゲーム内ショップで「スタミナ回復薬」を一度に購入できる個数は **1〜99個**（整数のみ）とする。購入数に応じて以下の割引が適用される。
* 1〜9個：割引なし（定価）
* 10〜49個：10%割引
* 50〜99個：20%割引

**設問：**
1. 同値分割法で「有効パーティション」と「無効パーティション」をすべて挙げ、代表値を1つずつ決めよ。
2. 2値境界値分析（2値BVA）で必要なテストデータ（境界値）をすべて挙げよ。

#### 演習2：デシジョンテーブルテスト（レイドボス討伐報酬の判定）
**仕様：** マルチプレイのレイドボス戦終了時の報酬ルールは以下の通り。
* 討伐に失敗した場合、与ダメージやアイテム使用に関わらず「参加賞」のみ付与する。
* 討伐に成功した場合、「討伐報酬」を付与する。さらに、与ダメージが全体の10%以上なら「MVPボーナス」を追加付与する。
* 討伐に成功し、かつ「報酬ブースト薬」を使用していた場合、獲得できる「討伐報酬」の個数を2倍にする（MVPボーナスは2倍の対象外とし、通常通り1倍で付与する）。

**設問：** 条件とアクションを整理し、不要な重複をまとめたデシジョンテーブル（判定ルール）を作成せよ。

#### 演習3：状態遷移テスト（期間限定イベントミッション）
**仕様：** 期間限定ミッションには「未達成」「受取可能」「受取済」「期限切れ」の4つの状態がある。有効な遷移は以下の3つのみである。
* 「未達成」→（達成条件を満たす）→「受取可能」
* 「受取可能」→（受取ボタン押下）→「受取済」
* 「受取可能」→（イベント受取期間終了）→「期限切れ」

**設問：**
1. 全遷移カバレッジを意識したとき、新人QAが必ず確認すべき**「無効な遷移（バグになりやすい操作）」**を2つ挙げよ。
2. テストケースを設計する際、無効な遷移を1つのテストケースに複数まとめてはいけない理由は何か。

---

### 演習の解答と新人QA向け解説

#### 演習1の解答・解説（同値分割法 ＆ 境界値分析）
* **(1) 同値分割法（計5パーティション）：**
  * 有効パーティション（3つ）：「1〜9個（例：5）」「10〜49個（例：25）」「50〜99個（例：70）」
  * 無効パーティション（2つ）：「0個以下（例：0、-1）」「100個以上（例：100）」
    *※数値以外（空欄・小数・文字列）が入力可能なUIならそれも無効パーティションに追加。*
* **(2) 2値BVAのテストデータ（計8個）：** **0, 1, 9, 10, 49, 50, 99, 100**
* **新人QAへのポイント：** 現場では「10個以上」をエンジニアが誤って `> 10`（11個以上）と実装するミスが頻発します。また、無効値の「0個」「100個」でボタンが非活性になるか、エラーメッセージが正しく出るかを確認するのが重要です。より厳密な3値BVAを行う場合は、各境界の両隣（2, 8, 11, 48, 51, 98等）も追加します。

#### 演習2の解答・解説（デシジョンテーブルテスト）
討伐失敗時は他の条件が結果に影響しないため「-（無関係）」として1列に統合でき、全5ルールで100%網羅できます。

| 条件 / アクション（レイドボス報酬） | R1 | R2 | R3 | R4 | R5 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| 条件1：討伐に成功した | T | T | T | T | F |
| 条件2：与ダメージ10%以上 | T | T | F | F | - |
| 条件3：報酬ブースト薬を使用 | T | F | T | F | - |
| **アクション：参加賞を付与** | | | | | **X** |
| **アクション：討伐報酬（通常）を付与** | | **X** | | **X** | |
| **アクション：討伐報酬（2倍）を付与** | **X** | | **X** | | |
| **アクション：MVPボーナス（通常）を付与** | **X** | **X** | | | |

* **新人QAへのポイント：** 仕様書を文章のまま読むと「討伐失敗時にブースト薬は消費されるのか？」「MVPボーナスはブースト薬使用時も付与されるのか？」といった抜け漏れや曖昧さに気づきにくいですが、表に起こすことでプランナーへ事前に質問できるようになります（シフトレフトの実践）。

#### 演習3の解答・解説（状態遷移テスト）
* **(1) 確認すべき無効な遷移の例：**
  * **「受取済」状態で再度「受取ボタン」を押下（連打・通信遅延時の再送含む）：** 報酬が二重付与されないこと。
  * **「期限切れ」状態で「受取ボタン」を押下（期間終了直前に開いた画面のまま操作）：** エラーになり報酬が受け取れないこと。
  * **「未達成」状態で「受取ボタン」を押下：** ボタンが押せない（または無効）こと。
* **(2) 1テストケースにつき無効な遷移を1つにする理由：** **欠陥のマスキング**（あるバグが原因でテストが止まったり異常な状態になったりして、別の無効遷移に潜むバグの発見を妨げてしまう現象）を防ぐためです。
* **新人QAへのポイント：** ソーシャルゲームでは「期間終了の1秒前に画面を開いておき、終了後にボタンを押す」ような境界時刻×無効遷移の操作で重大な不具合（不正なアイテム取得など）が起きやすいため、状態表を作って無効セルを必ず潰す習慣をつけましょう。

## 第5章 テスト活動のマネジメント

### 5.1 テスト計画・開始/終了基準・見積り・ピラミッドと四象限

**テスト計画書**は、テストの範囲・スケジュール・人員・リスク・テストアプローチ・環境要件を明文化し、関係者と合意するための設計図です。各テストレベルには、作業を始める条件である**開始基準（Readyの定義）**（例：テスト環境デプロイ完了、スモークテスト合格）と、完了を宣言する条件である**終了基準（Doneの定義）**（例：優先度High以上の未解決バグ0件、要件カバレッジ100%）を定めます。

#### 4つのテスト工数見積り技法
* **比率に基づく見積り：** 過去イベントの実績比（例：開発工数3：テスト工数2）から算出。
* **外挿：** 直近3回のイベントのテスト実績平均から、次回イベントの工数を予測。
* **ワイドバンドデルファイ（プランニングポーカー）：** 複数のQA・開発メンバーが独立して見積り、認識のズレを議論して合意形成する。
* **三点見積り：** 楽観値（$a$）、最頻値（$m$）、悲観値（$b$）から期待値と誤差を算出する。

> **三点見積りの計算例（新コラボイベントのシステムテスト工数）**
> 楽観値 $a = 6$ 人日、最頻値 $m = 9$ 人日、悲観値 $b = 18$ 人日 の場合：
> $$E = \frac{a + 4m + b}{6} = \frac{6 + 36 + 18}{6} = 10 \text{ 人日}$$
> $$SD = \frac{b - a}{6} = \frac{18 - 6}{6} = 2 \text{ 人日}$$
> → 見積り範囲は **8〜12人日（$10 \pm 2$ 人日）**

#### テストピラミッドとテストの四象限
* **テストピラミッド：** 自動テストの配分指針。下層（高速で壊れにくいユニットテスト）を最も多く、上層（低速で保守コストが高いUI/E2Eテスト）を少数に保ちます。
* **テストの四象限：** 「技術指向 vs ビジネス指向」「チーム支援 vs プロダクト批評」の2軸で、自動単体テスト（第1）、機能/ストーリーテスト（第2）、探索的・使用性テスト（第3）、負荷・セキュリティ等の非機能テスト（第4）のバランスを整理します。

### 5.2 リスクマネジメント（リスクベースドテスト）

リスクは**「発生可能性 × 影響度（損害）」**でリスクレベルを評価します。納期や体制に関わる**プロジェクトリスク**（イラスト納品遅延、QA人員不足、ストア審査遅延など）と、ゲーム品質に関わる**プロダクトリスク**（課金二重請求、セーブデータ消失、ガチャ確率誤表記、イベント進行不能など）を区別して管理します。

**リスクベースドテスト**では、リスクレベルが高い領域（課金・ガチャ・データ引き継ぎ等）から優先的にテストを実行し、手厚いテスト技法や熟練QAを割り当てて残存リスクを最小化します。

### 5.3 モニタリング・コントロール・完了とメトリクス

テスト実行中は、テストケース消化率、合格/不合格数、バグ発見・修正件数、残存リスクなどの**メトリクス**を継続的に収集（**モニタリング**）し、遅れや想定外のバグ急増があれば優先順位の変更や人員追加などの対策（**コントロール**）を打ちます。日々の状況は**テスト進捗レポート**（ダッシュボードやチャット含む）で共有し、リリース前には最終品質と残存リスク・教訓をまとめた**テスト完了レポート**を作成してリリース判定の材料とします。

### 5.4 構成管理

ソーシャルゲームでは「アプリ本体バージョン」「アセットバンドル」「サーバーAPI」「マスタデータCSV」「テストケース」が頻繁に更新されます。**構成管理**によりすべての成果物に一意のバージョンを付け、承認済みの組み合わせ（**ベースライン**）を管理することで、「どのバージョンのアプリとマスタでテストしたか」の追跡や、不具合発生時の過去状態の再現が可能になります。

### 5.5 欠陥マネジメント（伝わるバグレポートの書き方）

発見した不具合は、起票 → 解析・分類 → 修正対応 → 確認テスト → クローズという一貫したワークフローで管理します。エンジニアが即座に原因を特定できるよう、バグチケットには以下の情報を漏れなく簡潔に記述します。

* **一意のIDと簡潔なタイトル：** 「【バトル】特定キャラの必殺技発動時にアプリが強制終了する」
* **環境・ビルド情報：** 端末名（例：iPhone 15 / Pixel 8）、OSバージョン、アプリビルド番号、マスタバージョン、テストアカウントID。
* **再現手順・頻度・証跡：** 誰でも同じ現象を起こせるステップ、発生頻度（3/3回など）、スクリーンショット・動画・通信ログ。
* **期待結果と実際結果：** 仕様書上の正しい挙動と、実際に起きた挙動の対比。
* **重要度（Severity）と優先度（Priority）：** 「システムへの影響の大きさ（重要度）」と「どれだけ急いで直すべきか（優先度）」を区別する。例えば、タイトルロゴの誤字は機能影響が小さく重要度は低いが、リリース直前なら優先度は最高になる。

## 第6章 テストツール

### 6.1 テストを支援するツールの分類

ソーシャルゲームの開発・運用では、目的に応じて多様なツールを組み合わせて効率化を図ります。

| ツール分類 | ソーシャルゲーム現場での活用例 |
| :--- | :--- |
| **マネジメントツール** | テストケース管理、進捗集計、バグチケット管理（起票〜クローズのワークフロー管理）。 |
| **静的テストツール** | ソースコードの静的解析（Lint）、マスタデータCSVの型・範囲・参照整合性の自動チェッカー。 |
| **テスト実行・カバレッジツール** | 単体テストフレームワーク、実機自動操作ツール（リグレッションテストの夜間自動実行）。 |
| **非機能テストツール** | 大型イベント開始時の同時ログインを再現する負荷テストツール、通信の脆弱性診断ツール。 |
| **DevOps / コラボレーションツール** | 自動ビルド・自動デプロイのCI/CDパイプライン、チャット通知、仕様書Wiki、表計算ソフトなど。 |

### 6.2 テスト自動化の利点とリスク

テスト自動化は強力な武器ですが、「ツールを入れれば自動でバグが消える」という魔法ではありません。利点とリスクを冷静に見極めて導入します。

* **利点：** 毎回のイベント前に行う定型リグレッションテストの大幅な時間短縮、単純な操作ミス（ヒューマンエラー）の防止、カバレッジなどの客観的指標の取得、QA担当者がより高度な探索的テストや面白さの検証に集中できる時間の創出。
* **リスク：** UIや演出の変更が激しいソーシャルゲームでは、自動テストスクリプトの**保守コストが膨大になりやすい**。また、ツールへの過信による人的思考の軽視、導入・学習コストの見積り甘さ、手動テストの方が向いている領域（演出の違和感、操作の手触りなど）への誤用、ツールベンダーのサポート終了やOSアップデート非対応リスクに注意が必要。

## 研修ふりかえり：実務で意識すべき5つの行動指針

1. **「動かす前」にバグを潰す：** 企画書やマスタデータCSVの段階で疑問を挙げ、シフトレフトを実践する。
2. **「仕様通り」の先を見る：** 検証だけでなく、プレイヤーが楽しく安心して遊べるか（妥当性確認）を常に問う。
3. **リスクと技法でメリハリをつける：** 全数テストは不可能。課金・確率・データ保全などの高リスク領域に技法と工数を集中する。
4. **再現できる明確な報告をする：** エンジニアを責めず、環境・手順・期待結果と実際結果を整理して建設的に伝える。
5. **チーム全員で品質を作る：** QAだけでなくプランナー・エンジニアと対話し、イベントごとのふりかえりで仕組みを改善し続ける。
