## 4.1 テスト技法の3分類

勘や思いつきだけでテスト項目を作ると、漏れや重複だらけになります。シラバスでは、少ないテストケースで高い網羅性を得るための技法を、以下の3つに分類しています。

- **ブラックボックステスト技法**（仕様ベース）
- **ホワイトボックステスト技法**（構造ベース）
- **経験ベースのテスト技法**

---

## 4.2 ブラックボックステスト技法（4技法の実践例）

### ① 同値分割法（EP）

同じ処理が行われる入力値をグループ（パーティション）に分け、各グループから代表値を1つずつテストします。仕様で許可された「有効パーティション」だけでなく、エラーになるべき「無効パーティション」も必ず含めます。

> **例（未成年者の月額課金上限仕様）**  
> 「16歳未満：上限5,000円」「16歳以上18歳未満：上限20,000円」「18歳以上：上限なし」の場合、有効パーティションは3つ（例：12歳、17歳、25歳）、無効パーティションはマイナス値や不正な生年月日（例：-1歳、未来の日付）を設定し、各代表値でテストします。

### ② 境界値分析（BVA）

バグが最も起きやすいパーティションの「境目（最小値・最大値）」を狙う技法です。境界値と隣接する1点を見る**2値BVA**と、境界値の両隣を見るより厳密な**3値BVA**があります。

> **例（ガチャ天井カウント仕様）**  
> 「1〜299回は通常抽選、300回で天井報酬獲得」の境界（299と300）をテストする場合、2値BVAでは「299, 300」、3値BVAではさらに「298, 299, 300, 301」を確認します。「`if (count == 300)`」と「`if (count >= 300)`」の実装ミスなどを確実に仕留められます。

### ③ デシジョンテーブルテスト

複数の条件の組み合わせによって結果が変わる複雑なルールを表に整理し、組み合わせの漏れや仕様矛盾を発見します。

| 条件／アクション（イベント特効ボーナス） | ルール1 | ルール2 | ルール3 | ルール4 |
| :--- | :---: | :---: | :---: | :---: |
| 条件1：イベント開催期間内である | T | T | T | F |
| 条件2：特効キャラを編成している | T | T | F | - |
| 条件3：月額パスに加入している | T | F | - | - |
| **アクション：獲得ポイント 2.0倍** | **X** | | | |
| **アクション：獲得ポイント 1.5倍** | | **X** | | |
| **アクション：獲得ポイント 1.0倍（通常）** | | | **X** | **X** |

※ `T` = 真（条件を満たす）、`F` = 偽、`-` = 結果に無関係、`X` = そのアクションが発生。

### ④ 状態遷移テスト

システムの状態とイベントによる移り変わり（状態遷移図・状態表）をテストします。すべての状態を通る**全状態カバレッジ**、正しい遷移をすべて通る**有効遷移カバレッジ**、さらに禁止操作も試す**全遷移カバレッジ**があります。

> **例（クエスト進行の状態遷移）**  
> 「未挑戦 →（開始）→ 挑戦中 →（ボス撃破）→ クリア」「挑戦中 →（通信切断）→ 中断中 →（再開）→ 挑戦中」といった有効遷移に加え、「クリア済み画面でバックキー連打して報酬を二重取得できないか」などの**無効な遷移**も1テストケースにつき1つずつ検証します。

## 4.3 ホワイトボックステスト技法

ソースコードの内部構造を見て網羅率（カバレッジ）を測ります。コード内のすべての実行可能な行を通す**ステートメントカバレッジ**と、if文のTrue/Falseなどすべての分岐を通す**ブランチカバレッジ**があります。

> **重要ポイント**  
> ブランチカバレッジ100%を達成すればステートメントカバレッジ100%も自動的に保証されますが、逆は成り立ちません。例えば「属性相性が有利ならダメージ1.5倍（if文のみ、elseなし）」のコードでは、有利属性だけテストすれば全行通過（ステートメント100%）になりますが、不利・等倍時の分岐（ブランチ）が未テストのまま残ってしまいます。

## 4.4 経験ベースのテスト技法

仕様書に書ききれない現場特有のバグを見つけるため、QA担当者の知識と経験を活かします。

- **エラー推測（フォールト攻撃）：**  
  「ソシャゲでありがちなバグ」を先読みして突きます。例：日付跨ぎ（0:00／4:00リセット）、端末時刻の手動変更、決済ボタン連打、ガチャ演出中のタスクキル、機内モード切替、絵文字・特殊文字のニックネーム入力など。
- **探索的テスト：**  
  アプリを触って学習しながら、テスト設計・実行・評価を同時に進めます。時間枠（例：60分）と目的（テストチャーター：「新キャラのスキルが既存ボス全種に与える挙動を探る」）を決めて行うセッションベースドテストが効果的です。
- **チェックリストベースドテスト：**  
  過去の不具合知見を質問形式のリスト（「アプリをバックグラウンドから復帰した際、BGMは正常に鳴るか？」等）にまとめ、定期的に更新しながら使います。

## 4.5 コラボレーションベースのテストアプローチ

バグを「見つける」だけでなく、チーム全員の対話で「未然に防ぐ」アプローチです。ユーザーストーリーを**3つのC**（カード・会話・確認）と**INVEST基準**（独立・交渉可能・価値・見積り可能・小さい・テスト可能）で共同執筆し、受け入れ基準をシナリオ指向（Given/When/Then）やルール指向で明確化します。実装前に受け入れ基準からテストケースを作る手法が**受け入れテスト駆動開発（ATDD）**です。
