## 3.1 静的テストの基本と価値

静的テストは、ゲームを実行せずに成果物（企画書、イベント仕様書、マスタデータCSV、シナリオテキスト、ソースコード、テストケースなど）を評価する活動です。人間の目で行う**レビュー**と、ツールで機械的に調べる**静的解析**があります。

動的テストでは見つけにくい「仕様書の矛盾・曖昧さ」「到達不能なデッドコード」「コーディング規約違反」「シナリオの誤字脱字・禁則文字」を、実装前の最もコストが安い段階で直接発見できる点が最大の価値です。

---

## 3.2 レビュープロセス・役割・4つのレビュー種別

レビューは以下の5ステップで進めます。

```
計画 → 立ち上げ → 個々人のレビュー → 共有と分析 → 修正と報告
```

### レビューでの主な役割

- **マネージャー：** リソース提供・何を対象にするかの決定
- **作成者：** 仕様書やコードの作成・修正
- **モデレーター：** 進行管理・安全な場の維持
- **書記：** 指摘や決定事項の記録
- **レビューア：** 成果物の精査
- **レビューリーダー：** レビュー全体の責任

### 4つのレビュー種別

| レビュー種別 | 特徴とソーシャルゲーム現場での使い分け |
| :--- | :--- |
| **非形式的レビュー** | 決まった手順や記録は不要。隣席のプランナー同士でのチャット相談やペアプログラミングでの軽い確認など、手軽にミスを拾う。 |
| **ウォークスルー** | 作成者が主導して成果物を説明。新イベント企画書をプランナーがエンジニア・QAに読み合わせし、認識合わせと疑問点の洗い出しを行う。 |
| **テクニカルレビュー** | モデレーターが主導し、技術専門家が参加。マルチプレイの通信設計やDB負荷対策など、技術的な妥当性の合意と欠陥検出を行う。 |
| **インスペクション** | 最も形式的でメトリクス収集も行う。作成者はリーダーや書記を兼ねられない。課金決済仕様書やガチャ確率マスタなど、失敗が許されない重要成果物に適用。 |

> **レビュー成功のコツ**
> 「作成者の人事評価に使わない」「一度に大量の仕様書を見ず小さく分割する」「事前読み込みの時間を確保する」「チェックリストを活用し、心理的安全性を保つ」ことが不可欠です。
